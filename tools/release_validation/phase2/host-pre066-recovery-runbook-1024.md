# Limited PRE066 manual recovery

This is a concrete manual recovery boundary for review, not an executed recovery and not a callable automatic rollback. The old synthetic recovery helpers must not be used as host proof. Production approval must explicitly include this runbook before execution.

Eligibility requires all of the following independently checked while holding `/srv/clothinkai/production-20261018/flow78-release.lock` and the existing state journal lock: exact instance/disk/boot/input/active claim; journal prefix and all result hashes; **no MIGRATE intent at all**, no 067 head, no replacement/start/open intent, no possible new writes; independently observed head exactly `066_platform_metric_setting`. An unresolved prior intent must first be reconciled against its fixed observations; an unknown result is HOLD and this runbook cannot clear it. Any migration attempt, backend/lock ambiguity, 067 commit or new-write possibility forbids database restore and requires separate investigation.

Use only the six immutable IDs in the approved `state/host-input.json` baseline and the recorded original image IDs. Each ID is 64 lowercase hexadecimal characters and must still inspect to the recorded name/image. Docker commands below use the fixed prefix `/usr/bin/docker --host unix:///var/run/docker.sock --config /srv/clothinkai/production-20261018/docker-client`; never substitute mutable names or select by image. No `down`, volume/network removal, database restore, role alteration or pg_terminate_backend is permitted.

Recovery order after the eligibility proof:

1. Keep maintenance closed, restart=no, beat/worker stopped and timers disabled. Re-read original dashboard ID/network/aliases and original web mount. If the API is recorded SIGSTOP'ed, validate its original full ID/PID/start ticks/namespace and all target threads T using `host_producer_control.verify_frozen`. **Never SIGCONT it.** Use fixed `docker kill --signal KILL <baseline-api-full-id>`, then `docker wait <same-full-id>` must return 137; require no original PID/start identity and all three business-role connections zero. If the API was already stopped, verify those conditions without repeating a kill.
2. Confirm original API/worker/beat images and mounts are intact; PRE066 eligibility excludes all replacement actions, so no container recreation is required. Validate original beat DBM format/structure and bytes against `beat-before-manifest.json` where that snapshot exists. No reset, deletion or format conversion is allowed.
3. Start the original API only with `docker start <baseline-api-full-id>`. Its existing `/opt/production/start.py api` command requires schema066. Require original image, full ID, healthy `/health` and the real `/ready` JSON (`status=ok`, checks db/redis=ok), no OOM/restart and unchanged DB/Redis IDs.
4. Start original worker with `docker start <baseline-worker-full-id>` only if it was stopped. Verify exactly one worker, original task registration/queues and no duplicate old worker. Start original beat with `docker start <baseline-beat-full-id>` only if stopped, after original-store validation. Verify one original beat and seven tasks. These starts end the no-new-writes recovery window; any later failure must not trigger data restore.
5. Restore **only** the saved 2364-byte `state/old-active.conf`, SHA `4e9eeec6ebcca861e5861fd6306218750db5587d6c3c871afd65786162627fa8`, to fixed `ROOT/build/control/nginx-active.conf` using the existing protected `_atomic_replace` dirfd primitive. Require the current file to equal the known maintenance bytes, or a reconciled unchanged original. No generic copy/overwrite is allowed. Run `docker exec <baseline-web-full-id> nginx -t -c /opt/production/nginx-active.conf`, then `... nginx -s reload -c /opt/production/nginx-active.conf`; prove old workers exit, TLS/API readiness, dashboard route/member/snapshot timestamps and HTTP/HTTPS ACME readbacks.
6. Restore only restart policies from hash-bound `original-restart.json` using `docker update --restart=<original-policy> <same-original-full-id>`. Restore original timer enabled/active state with fixed systemctl enable/start commands only where the original snapshot says true; never unmask or start a service job directly. Revalidate fixed unit/script hashes, exact timer state and two stable windows.
7. Write a separate private manual-recovery receipt containing the original input/claim hash, reconciled action IDs, actual observations and operator approval reference. **Do not rewrite successful action rows or remove HOLD automatically.** While the global lock remains held, the operator may unlink only fixed `ROOT/flow78-active.json` after independently verifying that receipt and that the claim's device/inode/hash still match. Retain the lock inode, journal, all backups, migration/output directories and original snapshots. Automated `close_completed_claim` is solely for a verified full 29-step success and is not a manual-recovery shortcut.

If any prerequisite or observation is unknown, retain maintenance as far as its known state permits, retain the durable claim and stop. This runbook has no authority to recreate or roll back schema067.
