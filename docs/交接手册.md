## 4. 故障注入

台账的规矩：测试写完，往被测代码里注入一个真实形态的故障，确认测试会红。做法：

- 在容器里把代码复制到 `/tmp/app`，只改副本；源码按只读挂载（`-v "...\backend:/app:ro"`），不存在「忘了恢复」
- `$env:TEMP\ciwork\inject.py` 维护一个字典：注入名 → (相对路径, 原文, 替换文)。原文必须恰好命中一次，否则直接报错，
  免得「没注进去所以是绿的」。现有文件里是 PR #29 的 7 个注入，可以照着写
- `fi2.sh <注入名> <测试文件…>`：复制 → 注入 → 只跑指定测试，结果写 `$env:TEMP\ciwork\fi2_<注入名>.txt`
- 注入和跑测试严格串行；每个注入抓到几条红，写进台账对应批次

```sh
# fi2.sh
. /work/env.sh
name="$1"; shift
mkdir -p /tmp/app
cp -r /app/app /app/tests /app/alembic /app/alembic.ini /app/pyproject.toml /tmp/app/
[ -f /app/pytest.ini ] && cp /app/pytest.ini /tmp/app/
cd /tmp/app && export PYTHONPATH=/tmp/app
python /work/inject.py "$name" || exit 1
pytest -p no:randomly -q --no-cov -o addopts="" -p no:cacheprovider "$@" > /work/fi2_$name.txt 2>&1
echo "$name rc=$?"; grep -E "passed|failed|error" /work/fi2_$name.txt | tail -1
```

## 5. 生产只读核对

- 用 Zeabur MCP（`mcp_zeabur_*`）。项目 / 环境 / 服务 ID 在本地 `deploy-secrets.local.md`（gitignore，**含密钥**，
  只取 ID，别回显其余内容）；交接 prompt 里也给了
- 查库：在 backend 服务上 `execute_command`，跑容器里的 `psql "$DATABASE_URL_SYNC"`。SQL 和输出都走 base64，
  免得引号和中文在几层转义里出错：

  ```powershell
  # 本地：SQL 先写进文件再编码
  $b64 = [Convert]::ToBase64String([IO.File]::ReadAllBytes("$env:TEMP\ciwork\x_checks.sql"))
  ```

  ```text
  execute_command(serviceId=<backend>, environmentId=<production>, command=[
    "sh", "-c",
    "echo <b64> | base64 -d > /tmp/x.sql && psql \"$DATABASE_URL_SYNC\" -f /tmp/x.sql 2>&1 | grep -v '^Pager\\|^Output format\\|^Field sep\\|^Tuples' | base64 -w0; rm -f /tmp/x.sql"
  ])
  ```

  ```powershell
  # 本地解码
  [Text.Encoding]::UTF8.GetString([Convert]::FromBase64String("<输出>"))
  ```

- SQL 文件开头固定这几行。业务表开了 RLS，要先设租户（生产只有 1 个租户，`SELECT id, code FROM tenant` 可查）：

  ```sql
  \pset pager off
  \pset footer off
  \pset format unaligned
  \pset fieldsep ' | '
  SELECT set_config('app.tenant_id', '<租户 id>', false) AS t \gset
  ```

- 单次输出超过约 2,500 个 base64 字符会被截断：一批少查几条
- 跑 Python：同样 base64 传进去，`cd /app && PYTHONPATH=/app python /tmp/x.py`
- **只跑 SELECT**。PR #28 / #29 做过「真实服务代码在事务里走一遍再回滚」的生产演练，这类会碰写路径（PR #28 还真上传
  到 R2 再删掉），做之前先征得用户同意
- 不打印任何环境变量的值（`DATABASE_URL_*`、R2 key 等）
- 部署状态与日志：`get_deployments`、`get_build_logs`、`get_runtime_logs`；健康检查 `https://clothinkai-api.zeabur.app/ready`

## 6. 提交与发布

- 永远走新分支 + PR，不直接推 main。用户 10-07 批准执行计划后：分支上提交、push、开 PR 可以直接做；
  **合并（= 上生产）每次都要用户明确同意**。计划外的提交仍先问
- 合并 main = Zeabur 自动重新部署 4 个服务（只改文档也会）。backend 启动先跑 `alembic upgrade head`，迁移失败就起不来
- 合并后先用 `get_deployments` 确认 4 个服务都有合并时间之后的新部署。10-12 #44 合并时 Zeabur 接口正报「no available server」，GitHub App 的 push 事件丢了，
  4 个服务都没建部署。补救：再合并一次（例如下一个文档 PR），正常触发部署；10-13 合并 #45 后 4 个服务正常部署、063 上线，补救有效。不要用 `redeployService`（只重启旧镜像），
  也不要用 `deployFromSpecification`（会改写启动命令：backend 不跑迁移、celery 起成 uvicorn）
- 中文提交信息写进 `.tmp-zeabur/commitmsgNN.txt`（gitignore）再 `git commit -F`，避开 PowerShell 的引号与编码问题。
  标题照 `git log` 的格式（`fix(report): 中文摘要`），squash 合并时 GitHub 会补上 `(#PR号)`
- `git push -u origin <分支>` 偶尔卡住不返回：用 `git ls-remote origin <分支>` 确认推没推上去
- PR 用 GitHub MCP（`zizuiliaoya-droid/clothinkai`，base `main`），偶发 `fetch failed` 直接重试。描述写改了什么、
  怎么测的、对生产的影响
- CI 绿了、用户同意后 squash 合并，带 `expectedHeadSha`；之后本地 `git checkout main; git pull`
- 合并后：等 4 个服务部署完 → `/ready` → 生产只读核对这次改动 → 回写台账（「已完成」表、批次小节、「当前进度」）
- **分支叠着做的合并方法**：后一个分支建在前一个还没合并的分支上（10-13：R5 建在 R4 上，R6 建在 R5 上；PR-6 建在 PR-5 上）。
  前一个 squash 合并后，在后一个 worktree 里 `git fetch` 再 `git rebase --onto origin/main <前一个分支的本地 HEAD>`；然后比较 `backend` / `frontend` 两棵树
  和验证过的提交是否逐字相同（`git rev-parse <提交>:backend`），相同就不用本地重跑全量，看 CI。GitHub 的「更新分支」会在远端 PR 分支上做一次合并提交，
  本地分支就和远端不一致了：不要强推，squash 合并照常可用
- 迁移：编号从 057 起按合并顺序取；本地验证 downgrade → upgrade 往返，和测试串行跑（并行会死锁）；
  改汇总表列或口径的迁移要清空 `report_summary_coverage`（054 定的规则）

收尾：PR 合并后删 worktree、删本地分支、删测试库。**删 worktree 之前先拆联接**：`cmd /c rmdir ".worktrees\<名字>\frontend\node_modules"`
（不带 `/s`，只删联接本身），确认主工作区的 `frontend\node_modules` 还在，再 `git worktree remove .worktrees/<名字>`。直接删的话，
Windows 上的 git 会顺着联接把主工作区的依赖一起删掉（10-07 真的发生过，见台账「踩过的坑」）。

10-08 收尾时又遇到三件事：
- squash 合并后用 `git rebase --onto origin/main <上一个分支的 HEAD>` 移植后一个分支之前，先确认 `git fetch` 成功、
  `origin/main^{tree}` 等于刚合并分支的 tree；fetch 失败时 origin/main 还是旧的，rebase 会撞冲突（当时立即 `--abort`）
- `git worktree remove` 可能删到一半报 Permission denied（有进程占着某个子目录）：git 已注销这个 worktree，剩下的是已入库文件的副本。
  先用 `Get-ChildItem -Recurse -Force -Attributes ReparsePoint` 确认里面没有联接，再删；删不掉的空目录等占用的进程退出再删
- 主工作区出现过 15 张已入库图片被删（不是用户删的，来源没查到），`git restore` 找回。收尾时看一眼主工作区的 `git status`

工作流中断（例如模型用量上限）后续跑：先看 worktree 的 `git status` / `git log` 和计划文件里的进度记录，判断做到哪；必要时把分支 rebase 到最新
main（先 `git stash push -u`，rebase 后 `git stash pop`；动手前确认与 main 新改的文件没有重叠）；再用简报文件 + 「接着做、不要从头来」重新启动。

## 9. 工作流规则（2026-10-07 起：少做重复功，效果不打折）

10-07 的会话日志统计（脚本 `C:\Users\54566\AppData\Local\Temp\ciwork\sess_stats*.py`）：一天 3,880 credits，87% 花在写计划、写设计、

而大设计文档在单个会话里被反复读了 15~25 次。测试和等审批都不是瓶颈。据此定下这些规则，测试先行、故障注入、全量检查、
一次独立评审这些真正起作用的环节都保留。

按任务大小选流程：

| 任务 | 流程 |
|---|---|
| 小：≤ 2 人日的修复或小功能 | 一个 coder 步骤（先自己列一页以内的清单）→ 一次语义评审，最多再修一轮 → 收尾。不单设 planner |
| 中：2 ~ 6 人日，或跨前后端多个模块 | planner 写 ≤ 15 KB 的计划（决定、文件 / 函数指针、测试与注入清单，不写到行级代码）→ 每个条目一个 coder 步骤 → 收敛循环（修复 → 评审，≤ 3 轮）→ 收尾 |
| 大或有歧义：新状态机、权限、数据模型 | 先设计（每节写完就落盘），设计评审 ≤ 2 轮且只看改动，然后按「中」做。7c / 7d 这种超大的：总设计不再扩写，每个 PR 开工前从总设计摘出相关小节，写成一份短实施简报 |

其他规则：

- 推理强度显式设置：workflow 默认 `high`；建目录、提交、写报告这类步骤用 `low` / `medium`；只有真正难的设计决策用 `xhigh` / `max`。
  不设就会继承编排会话的强度
- 并行最多两路，按优先级排；接近用量上限时改成串行。多开几路不会更快，只会被一起打断
- 简报写成文件，启动 prompt 只写要点和简报路径；每个步骤先读 [开发须知](开发须知.md)，再读简报和简报点名的小节
- 评审只看本轮改动；HIGH / MEDIUM 才进下一轮；评审是循环的最后一步；`onMaxIterations` 用 `pause`
- repeat 循环至少跑一轮：前面已经单独评审过的，后面就别再接评审循环（10-07 因此多跑了一轮）
- 实现步骤一步一个条目，做完就提交；进度写进计划或 FEAT 文件，中断后照它续跑
- 编排会话：不轮询，收到通知再处理；文档改动攒一批再提交；上下文超过约 60%，或一批工作合并完，就换新会话接手（第 10 节）
