# 多租户内测开户与登录

本说明配套 2026-10-31 多租户补齐代码；发布前不可认为生产已有这些入口。本轮沿用数据库 069，不新建迁移。

## 登录方式

所有客户使用同一个系统地址。原客户打开 `/login`，租户代码留空即可，等同 `default`；账号密码保持原样。

新客户填写开户时约定的租户代码，例如 `customer-a`。可以直接给客户 `/login?tenant=customer-a` 链接，页面会预填租户代码。租户代码区分大小写，建议统一用小写字母、数字、短横线。不同租户可各自使用 `admin` 等同名账号，其密码、数据和登录失败计数分开。

管理员登录后在“系统管理 → 用户管理”创建的是本租户账号。当前不提供租户切换和公共自助注册；访问其他租户应退出后使用另一租户代码与对应账号登录。

## 运维开户

由运维在发布后的 API 运行环境执行，使用应用现有系统数据库连接。执行前按项目约定确认生产开户授权与租户名称、代码、管理员用户名；不要把连接串或密码贴进命令行。

在后端目录先预览（此步骤不连接数据库）：

```sh
python -m app.modules.auth.create_tenant --code customer-a --name "客户 A" --admin-username admin --expect-environment production --expect-database clothing_erp_prod_20261018
```

核对输出环境、主机、数据库、租户代码与用户名后，在同一命令末尾增加 `--apply` 执行。环境或数据库名与运行配置不符会拒绝执行；测试环境填写实际 development/staging 与测试数据库名，不能照抄生产参数。

创建租户、管理员、角色关联和开户审计在一个事务内完成。已占用的代码（含已软删除租户）不会覆盖，不会重置原账号密码。仅成功提交后返回一次随机临时密码，管理员首次登录必须修改。使用私密渠道交付，不将含密码的结果写入开发看板、Git、工单或公开日志。若连接错误造成提交结果不确定，先查租户状态；不要把重试当成重置密码工具。

新租户从空业务数据开始，不复制原客户商品、推广、财务或附件。当前只负责少量内测开户，不包含套餐、计费、配额管理与租户管理后台。

## 一次双租户验收

在测试数据库开两个租户 A/B，都使用管理员用户名 `admin`，设置不同密码；验证：

1. 带各自代码能登录，相同账号配另一租户密码被拒绝；原 default 账号省略代码仍可登录。
2. 首次登录强制改密；各租户自行建用户，仅能看到和修改自己的用户。
3. 两边分别建立少量测试业务数据；推广、报表等列表和附件访问互不混用。
4. 审计列表、筛选、总数仅显示本租户；将另一租户用户 ID 用作筛选也不能读到其日志。
5. 对 A 进行连续错密，B 的同名账号仍可登录。
6. 测试中将租户停用后，新登录、已有访问令牌与刷新令牌均被拒绝；不要在生产中为演示而停用正在测试的客户。

CI 覆盖同名登录、默认客户兼容、停用、审计记录/总数、重复开户和失败回滚；实际客户数据与附件流程由对应环境内测完成。
