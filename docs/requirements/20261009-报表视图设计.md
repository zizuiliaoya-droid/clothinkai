## 2. 每条需求的方案

通用约定（每条都适用，下文不重复）：比率一律读取时用 `safe_div` 现算，汇总表只存可加的量；分母 ≤ 0 返回 `null`，前端显示「—」；
可加量逐日存精确值（金额 `numeric`、点赞 `numeric`），取整在求和之后；每个读接口都有「汇总 / 实时」两条路径，用 `SummaryReadRepository.freshness` 整段二选一，
两条路径 `model_dump(mode="json")` 逐字相等。时间一律用租户时区（`DEFAULT_TENANT_TZ`）取「今天」。

### 2.1 7e-1 公共底座（R1 + R8）

**URL 带来的值不写回记忆**；用户手动改筛选后才写记忆，并 `replace` 掉 URL 参数。`schema` 是每页白名单（`preset`、`date_from`、`date_to`、`season[]`、`pr_id`、`goods_id`、`channel`、`tab`、`exclude_brushing`），

### 2.3 7e-3 单品投产（R3）

- **近 7 天**（默 10）：区间固定为「昨天往前 7 天」（T-7 ~ T-1），不随筛选变。`ProductionService.get_report` 多调一次 `_goods_rows`（同一份 SQL，汇总 / 实时各自判断，同现在的本期 / 上期），
  按（商品, 渠道）合并成 `recent7_pay_amount`、`recent7_total_spend`、`recent7_net_roi` 三列；列头写「近 7 天（MM-DD ~ MM-DD）」。刷单开关同样作用于近 7 天。
- **退货前投产比** = 支付金额 ÷ 总推广成本；**推广单件成交成本** = 总推广成本 ÷ 支付件数（默 11；替换 `services/metric/style_roi.py` 里恒为空的旧公式，旧函数删掉）；
  支付件数来自新列 `pay_orders`（千牛「支付件数」，刷单开关不扣件数，列头注明）。「待确认收货金额」改名「**实际销售金额**」（= 支付 − 成功退款）。
- **加购**：站内加购 = Σ`ad_add_cart_count`（万相台「总购物车数」）；站内加购成本 = 站内投放 ÷ 站内加购；总加购 / 总加购成本照旧。
  **站外加购** = max(Σ`paired_all_cart` − Σ`paired_ad_cart`, 0)，两个 paired 列只在「同一商品同一天千牛和万相台都有数据」的日子记值（第 3 节），区间求和后再相减取 0。
  `paired_days = 0` 时站外加购显示「—」，悬停说明「所选区间千牛与万相台没有同一天的数据」。生产现在就是这样（万相台只有 03-23，千牛没有 03-23）。
- **毛利**（默 12）：销售货品总成本 = 支付件数 × 当前单品货品成本（启用成员 `goods_style_item.single_goods_cost` 之和）；单品毛利 = 实际销售金额 − 销售货品总成本；
  单品利润率 = 单品毛利 ÷ 实际销售金额。成本读取时现算（不进汇总表），改价立即生效；任一启用成员没有成本 → 三列都为 `null`（不当 0）。
  三列按第 4 节字段级规则 F1 裁剪（`sku.cost_price` 的规则；PR 主管因此看不到毛利，列入第 11 节待确认），读不到给 `null`，导出同规则。
- **渠道拆行**（11-37）：主表行键从商品改成（商品, 渠道）。商品没有直播链接时只有「普通」一行，与现在逐字相同；有直播链接时拆两行，行内显示渠道标签。
  站外推广成本、刷单全部记在「普通」行（台账批次 6：小红书笔记的站外成本归普通渠道）。同渠道多条链接合在一行，行尾标「N 条链接」。
- **停用链接**（7e-9，问题 D）：`platform_product.is_active = false` 的链接，日报与万相台花费都不进单品（第 3 节刷新源改动）。页面标题栏显示「N 条链接已停用、未计入单品」
  （N = 区间内有日报或花费的停用链接数，接口 `ProductionReport.inactive_link_count`；汇总 / 实时两条路径共用同一条实时 SQL，不进汇总表），0 条时不显示。
- 导出：投产 sheet 加上述列，列顺序与页面一致；页面与导出共用一份列定义（`report/production_columns.py`）。

### 2.4 7e-4 店铺日 / 周 / 月（R4）

- **菜单**：「报表与分析」下改成「投产分析」分组：单品投产（`/production`）、店铺日明细（`/store/daily`）、店铺周汇总（`/store/weekly`）、店铺月度汇总（`/store/monthly`）；
  旧路由 `/store-daily` 重定向到 `/store/daily`（保留查询串）。BI 看板留在原处。
- **下钻**：月表点行 → `/store/weekly?date_from=<该行实际起>&date_to=<该行实际止>`；周表点行 → `/store/daily?…` 同理（带行上的实际起止）；都走 `useReportFilters`。
- **读取**：日 / 周 / 月三个接口 `GET /api/reports/store/{daily|weekly|monthly}`。**桶 = ISO 周（或自然月）∩ 请求区间**，行上标实际起止日期：
  - 完整落在区间内的桶：桶内每天有覆盖 → 读 `shop_week_summary` / `shop_month_summary` 的整桶行；否则该桶走实时；
  - 首尾被截断的桶：不读周 / 月表（它们存的是整桶）；截断后的日子全有覆盖 → 读 `shop_daily_summary` 在 service 里求和，否则实时日聚合求和；
  - 实时路径同样按「桶 ∩ 区间」分桶：同一个店铺日聚合方法按 `bucket_expr('week'|'month')` 分组，WHERE 用请求区间，天然只含截断后的日子。
  两条路径逐字相等（第 8 节「区间从周三开始」「区间不是整月」两个场景）。含今天的桶覆盖不全 → 实时。旧接口 `/api/reports/store-daily` 保留一个版本（旧前端兼容），返回结构不变。
- **公式**（PRD §9 + Q17）：实际销售额 = 支付 − 退款 − 刷单本金；站内推广费 = 万相台合计，某天手填了全站推 / 直通车 / 引力魔方任一项就用手填三项之和（默 13，按天判断再求和）；
  站外推广成本 = 当天合作日期的已发布推广单 `total_promo_cost`（全店，含没归属商品的单）；推广总额 = 站内 + 站外；推广总占比 = 推广总额 ÷ **支付总额**；站内占比 = 站内 ÷ 实际销售额；
  站外占比 = 站外 ÷ 实际销售额；净推广占比 = 推广总额 ÷ 实际销售额；净投产 = 实际销售额 ÷ 推广总额；投产（扣除刷单）=（支付总额 − 刷单本金）÷ 推广总额。
  全店口径：停用链接、未映射到商品的日报都算（问题 D）。「其中直播」两列（直播支付、直播站内花费）只展示，不参与上面任何公式（大盘剔除直播归批次 6）。
- **仅退款**（默 14）：`store_daily.refund_only_amount numeric(12,2) NULL`，按天存金额。日明细表行内编辑（运营 + 管理员，`report.store_daily:write`）。
  仅退款率 = Σ仅退款 ÷ Σ支付，**只算已录入的日子**（分子分母都只取 `refund_only_amount IS NOT NULL` 的日子），旁边显示「已录 x/y 天」。
  手填层不进汇总表，读取时 LEFT JOIN（两条路径一致），录完立即生效、不清覆盖。
- **手填三项的录入入口**：同一行内编辑，补上 `PUT /api/reports/store-daily/{day}` 的前端调用；`upsert_manual` 改按 `payload.model_fields_set` 判断，传 `null` 就清空（现在清不回空，C-15）。
  校验：金额 ≥ 0、≤ 99,999,999.99、两位小数，否则 422；`day` 不能晚于今天（422 `STORE_DAILY_FUTURE_DATE`）；备注 ≤ 200 字。写审计（谁、哪天、改前改后）。
- **日期并集**（要通知）：店铺日聚合的日期轴改成「千牛日报 ∪ 万相台 ∪ 已发布推广单合作日期 ∪ 刷单 ∪ `store_daily`」的并集，不再只列有千牛日报的日子。
  **刷新源改动在 R2 做**（与清覆盖同一个 PR，第 3.2 节）；R4 只做展示与通知。
- 「访客数」改名「商品访客数合计」（默 16），悬停说明会重复计。页面标题「支付订单数」改正为「支付件数」。

### 3.3 覆盖失效 helper（R2 建，R2 / R7 用）

`report/summary_invalidation.py::invalidate_summary_coverage(session, *, tenant_id, reason) -> int`：

1. 先 `current_setting('lock_timeout')` 记下原值，`set_config('lock_timeout', '30s', true)`，再 `SELECT pg_advisory_xact_lock(hashtextextended(CAST(:key AS text), 0))`，拿到后 `set_config` 还原（不影响业务事务后续语句）；键用刷新同一个 `_lock_key(tenant_id)`。**阻塞**而不是 try：
   要等正在跑的刷新提交。否则刷新事务拿着旧系数 / 旧链接状态算完、在我们删完覆盖之后才提交，会把旧数字连同覆盖记录一起写回去。刷新锁本身是 try，不会反过来等我们。
2. `DELETE FROM report_summary_coverage WHERE tenant_id = :t`，返回行数；`logger.info("report_summary_coverage_invalidated", tenant_id, reason, rows)`。
3. 等锁超时（`LockNotAvailableError`）→ 抛 `SummaryRefreshBusyError`，调用方整事务回滚，接口回 409 `REPORT_SUMMARY_REFRESH_BUSY`「报表正在刷新，请稍后再保存」，可重试，不报 Sentry。

调用方在**自己的业务事务里**调用（配置保存、链接启停），一起提交或一起回滚。刷新方在拿到锁之后才读配置与链接状态，所以锁释放后的下一次刷新一定读到新值。

系数 `0 < x ≤ 10`、最多 3 位小数；阈值整数 1 ~ 10,000,000；同一平台出现两次 422。值没变的行不写；有任何一行变了 → 同事务写审计（改前改后）+ `invalidate_summary_coverage(reason="platform_metric_setting")`，
