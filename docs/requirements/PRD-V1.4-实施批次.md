## 批次 2：合作模式 typed 化 + 三分支成本与流转

PRD 模块二的核心。**现状最大的问题是合作模式根本不是字段** —— 它存在 `promotion.source_extra` JSONB 的「合作方式」key 里，枚举只定义在前端 `PromotionListPage.tsx` 的 `SOURCE_FIELDS`，后端零校验。于是 PRD 里所有「后端必须做分支判断，不可只靠前端」的硬约束，一条都无法落地。

一个重要发现：**PRD 说的「主管审核」就是现在的 `PromotionService.review()`**，不是新环节。现有链路是 `发布 → 自动推进待核查 → 主管 review approve → 待付款 → 发 SettlementRequested → finance 建结款单`，PRD 要的只是在 approve 之后按合作模式走三个不同出口。所以这批是改造而非重写。

### 2a：合作模式字段 + 成本口径 ✅ 已完成（migration 046）

- `promotion.cooperation_mode` typed 字段 + `CooperationMode` 枚举，迁移时从 `source_extra['合作方式']` 回填并删掉 JSONB 副本（避免两处不同步）
- 字段可空：生产 5156 条里只有 2 条填了合作方式，5154 条历史「未发布」单没有这个信息。不编造默认值；service 允许从空补一次，补完即锁
- 单据已有模式后不可改：service 层拦截返回 409，不依赖前端禁用
- 新增 `return_shipping_fee`（寄回运费）
- `total_promo_cost` 用**数据库生成列**而非应用层重算 —— 写入路径有 HTTP / Excel 导入 / 迁移三条，手动重算迟早漏一条。配套给 `Promotion` 加 `eager_defaults`，否则 async session 访问生成列会抛 `MissingGreenlet`
- 成本三分支，后端强制覆盖前端传值：
  - 寄拍：`cost_snapshot = 0`
  - 送拍 / 置换：`cost_snapshot = SUM(goods_style_item.single_goods_cost WHERE is_active)`
  - 置换：`quote_amount = 0`
  - 区分了「建单初始化」与「更新兜底」两个方法：PRD 允许 PR 微调送拍/置换的样品成本，所以更新时只压那两个恒为 0 的字段，不重算汇总值覆盖人工录入
- 报表口径切到站外推广成本（`total_promo_cost`）共 5 处；`aggregate_promotion_summary` 的 4 处**保持** `quote_amount`，因为 PRD §9 定义「约篇金额 = 博主服务费合计」，与站外推广成本是两个口径
- 切口径时生产影响为 ¥0：报表只统计 `publish_status = '已发布'`，而生产只有 2 条已发布推广且样品成本为 0。趁数据少把口径改对
- 成本留痕**仍只记 `*_changed: true` 不记金额**：audit_log 的读取面只要 `auth.audit:read` 就能看全部，而金额本身受字段级权限保护（PR 看不到报价），写进 audit 等于绕过那层权限。金额级回溯应该做带权限的单据时间线表，不是放宽 audit 脱敏 —— 留到批次 4 跟催发留痕一起做

## 批次 4b-1：复盘环节 ✅ 已完成（migration 050）

- 新增 `metrics_recorded_at`：之前系统靠 `like_count IS NOT NULL` 当「信息完整」的

## 批次 5a：投产 SQL 性能修复 ✅ 已完成（无 migration）

进批次 5 之前先量了一次生产真实数据，结论推翻了原规划的前提，所以先做了这个。

### 原规划里两处说法要改

1. **「报表都是查询时现算」对，但「这些报表功能还没做」错。** 4 个报表（工作进度 /
   爆款约篇 / 店铺数据 / 投产）+ BI 看板**都已经实现了**，走 `advanced_repository.py`

2. **`shop_daily_data` 不能直接建** —— 已有 `store_daily` 表（018 建的），语义是

   `qianniu_daily` 聚合之上，是 override 层不是汇总层。再建一张同位表会打架。

### 生产实测：瓶颈不是数据量，是一条 SQL 的写法

| 表 | 行数 | 大小 |
|---|---|---|
| `qianniu_daily` | 310 | 552 kB |
| `ad_daily` | 38（只有 2026-03-23 一天） | 168 kB |
| `promotion` | 5156 | — |
| `goods_main` | 264 | — |
| `store_daily` | **0**（手填功能从没用过） | — |

耗时（生产实测，取 3 次最好）：

| 查询 | 耗时 |
|---|---|
| **投产 SQL（全区间）** | **1848ms** |
| 投产 extra fetch | 11ms |
| 工作进度 SQL | 11ms |
| 店铺数据 SQL | 0.7ms |
| `BiService.get_dashboard` | 365ms |

`EXPLAIN ANALYZE` 指出根因：

```
Nested Loop Left Join
  Join Filter: (EXISTS(SubPlan 1) OR ...)
  Rows Removed by Join Filter: 81550
  Buffers: shared hit=237381
```

映射逻辑内联在 `LEFT JOIN qianniu_daily ON (...)` 的条件里，于是 264 商品 × 310 日报
= 81,840 个组合**各跑一遍** EXISTS / NOT EXISTS / COUNT(DISTINCT)。23 万次 buffer
命中处理 310 行数据。

更刺眼的是：那段三层嵌套的 legacy 兜底占了 846→275ms 中的 **571ms（67%）**，而它
**只为 20 行日报服务**（`style.qianniu_product_id` 非空的款式只有 2 条）。

### 修法：把映射提成 CTE，不是建汇总表

`_QIANNIU_GOODS_LINK_CTE` 把「日报 → 商品」先物化一次（日报行数量级），主查询退化成
等值 JOIN。口径逐字对应，新增 7 条测试把四种映射情形钉死：正路 / FK 为空靠
platform_id 对上 / legacy 兜底唯一归属 / 兜底被护栏挡掉（同一千牛ID 落多个商品时
谁都不算）/ 套装共用一条链接只算一次 / 多天累加只出一行 / extra 脏值不炸。

CTE 用 `UNION` 而不是 `UNION ALL`：两条分支理论上互斥，但数据脏时可能同时命中，
去重保证日报不被算两次。

**生产实测结果（上线后同一份数据复测）**：

| | 优化前 | 优化后 | |
|---|---|---|---|
| 投产 SQL | 1848ms | **215ms** | 8.6x |
| `get_report`（含上期对比 + extra 聚合） | 1855ms | **173ms** | 10.7x |

口径不变的证据：`pay_amount` 合计 **¥151,358.40**，与批次 1b 以来每次核查的数字
逐分一致。

### 这件事改变了「要不要建 5 张汇总表」的判断

预聚合的唯一理由是性能，但：
- 数据量 310 行，汇总表没有可感知的读取收益
- 刷新任务**还是要跑同一条聚合 SQL**，SQL 不修，每小时跑一次照样慢
- 两份口径（实时 + 汇总）是新的 bug 源 —— 这个项目已经吃过「同一个值两处定义」的苦
  （`legacy_settings` 与 `scan_service` 的催发阈值、`like_count` 与 `source_extra['点赞数']`）

**所以 5 张汇总表的取舍需要业务方决定** —— 业务方选了「照 PRD 全建」，见下节。

## 批次 5b-1（已完成）：5 张中间汇总表 + 每小时刷新

migration `052_report_summary`。`product_roi_summary` / `pr_work_progress_summary` /

### 刷新源一律复用现有 repository 方法

汇总表最大的风险不是性能也不是调度，而是**预聚合口径和实时查询口径悄悄分叉** ——
数字对不上，不报错、不抛异常、没有任何信号。这个项目已经为「同一个值两处定义」

### 几个值得留痕的取舍

今天算催发的单子明天变超时，按历史日期固化下来永远是错的。这 5 个继续实时算，
读取时与汇总表结果合并。

**`store_daily` 的手填值不进汇总表**。那是人工 override 层（3 个广告消耗 + 备注），
读取时 LEFT JOIN 过去即时生效；存进汇总表反而要等下一次刷新才看得到自己刚填的值。
表名也刻意叫 `shop_daily_summary` 而不是 `shop_daily_data` —— 和 018 的 `store_daily`
同位会打架。

**多存一列 `brushing_amount`**。报表有「含刷单/剔刷单」开关，只存一个口径另一个就
查不了，为开关各存一份行则是把同一笔数据写两遍。存刷单额本身，两个口径都能从一份行
还原：含刷单 = `pay_amount`，剔刷单 = `pay_amount - brushing_amount`。为此
`daily_trend_by_goods` 的 brushing CTE 改成**总是计算**，减不减由 `:exclude_brushing`
在 aggregated 里决定。

**用「区间删 + 批量插」而不是 upsert**。纯 upsert 漏掉「源数据减少」：某天的千牛日报
被删或改了货号，那行汇总不会被任何 upsert 覆盖，永远停在旧数字上。要补这个漏，upsert
之后还得算出「本次没产出的 key」再删 —— 生产 264 商品 × 31 天是 8000 多个 key，拼进
SQL 会炸。先删后插一步到位，且删插同事务，MVCC 保证读取方看不到空表。

> **更正（5b-1 补丁）**：初版说「两个刷新撞上时最终写出同一份数据，不加锁」是错的。
> 「区间删 + 批量插」在 READ COMMITTED 下**不能并发** —— 后一个事务的 DELETE 看不到
> 前一个刚插入、尚未提交的行，它的 INSERT 会撞唯一索引。已改为刷新入口拿租户级
> `pg_try_advisory_xact_lock`，见下节「5b-1 补丁」。

**周/月刷新会把区间补全成桶**。只刷 3/10~3/15 却写「3 月」那一行，这行就只含 6 天，
月汇总凭空少掉大半。

### 权限：独立的 `report.summary:refresh`

手动刷新端点 `POST /api/reports/summaries/refresh` 横跨 5 张表且先删后建，挂在
`report.production` 或 `report.store_daily` 下，持单张报表读写权的人就能触发全表重算。

action 刻意取 `refresh` 而不是 `read`/`write`：`has()` 的通配按 action 精确匹配，
而 `operations` 与 `pr_manager` 都持有 `report.*:read` —— 叫 `read` 就会自动泄漏给他们。
这和谈款审核当初必须独立成 `negotiation` 一级域是同一类问题。查过全库：没有任何角色
持有 `report.*:*`。

### Beat 槽位

`refresh-report-summaries-hourly`，`crontab(minute=20)`，`queue="report"`。
minute=20 是为了避开整点的异常预警与 `*/15` 的采集恢复 —— 三个任务都要连库。
滚动窗口 31 天（覆盖「上月整月」，月桶才不会被半月数据覆盖）；更早的区间用手动端点补。

### 测试立的护栏

新增 33 条，重点是用**故障注入**确认它们真能抓到问题（测试绿了不等于有效）：

| 注入的故障 | 被抓到的测试 |
|---|---|
| 广告子查询丢掉商品维度（`NULL::uuid AS goods_id`） | 按日合计 ≠ 区间聚合、全商品切片 ≠ 单商品 |

| 周/月刷新不把区间补全成桶 | 月汇总被半月覆盖 |

另外每条等值测试都带一个「场景有效性」断言（四个指标必须都出现非零值），
防止在比对一堆 0 的情况下静默通过。

### 5b-1 补丁：刷新锁 + 覆盖记录 + 周月缺天（PR #24）

切读取之前复查刷新逻辑，又找出两个问题，加上切读取必需的覆盖记录，单独一个 PR：

**1. 并发刷新会撞唯一索引。** 每小时的定时任务撞上页面手动刷新就会触发。现在刷新入口
拿租户级 `pg_try_advisory_xact_lock`：
- 事务级 —— 随 commit / rollback 释放，进程崩了不会留死锁
- try 而不是阻塞 —— 拿不到就报忙（端点 409 `REPORT_SUMMARY_REFRESH_BUSY`）。排队会占住
  web worker 或 Celery 槽位，而生产 worker 只有 2 个并发还要跑采集与备份。定时任务撞锁时
  跳过这一轮、**不报 Sentry**（不然每次手动刷新都刷出一条告警，真故障被淹没）
- 租户粒度 —— 不同租户互不影响

还写了一条测试证明锁是必要的：绕过锁、两个事务交错执行删插，确实撞 `UniqueViolation`。
这条测的是前提而不是我们的代码 —— 以后有人觉得「看起来不需要锁」想删掉，它会说明原因。

**2. 周/月汇总缺月初几天。** 定时窗口是「今天往前 31 天」，下沿几乎总落在月中。生产第一次
刷新是 09-02 ~ 10-02，9 月这一行要由 09-01 起的日汇总加起来，但 09-01 不在窗口里，日汇总
从没写过那天 —— 9 月永远缺 09-01。生产上数字恰好是对的，只是因为 09-01 那天没有数据。

修法：店铺日汇总的刷新区间扩到完整周桶与月桶（`shop_daily_span`），周/月二次聚合也按
扩展后的区间重算，周/月行始终等于桶内日汇总之和 —— 月 → 周 → 日下钻各层对得上。
店铺日汇总只有一条查询（0.7ms），扩几天没有成本。

已有的「半个月刷新」测试**发现不了**这个问题：它先做了一次全量刷新，月初的日汇总已经在
表里。新测试刻意不做前置刷新，直接复现生产形态（注入后 9 月 = 500 而非 800）。

**3. 覆盖记录 `report_summary_coverage`（migration 053）。** 切读取后，「某天没有汇总行」
可能是那天没数据，也可能是从没刷过。不区分的话，没刷过的历史区间会**静默显示成 0**。
生产实测：汇总表只有 09-17 ~ 09-18 有行，而千牛日报从 2026-01-01、推广单从 2025-12 开始。

每次刷新给区间内**每一天**记一行，不论那天有没有数据；只记 ROI / PR / 店铺三张日表都刷过的
区间（店铺表为凑整桶多刷的那几天不算）。读取侧据此判断：覆盖了读汇总表，没覆盖回退实时。

053 **刻意不回填**。看似能按 052 已有的汇总行反推「哪些日子刷过」，但覆盖与「有没有数据」
无关：第一次刷新窗口 31 天，有汇总行的只有 2 天，反推会把另外 29 个「刷过但没数据」的日子
当成没刷过。不回填的代价只是首次刷新前多走几次实时聚合。

**PRD 对历史数据的口径**（核对原文）：「定时任务只处理最近 31 天，历史数据只能页面手动刷新」。
所以 31 天外的历史数字**不会自动更新** —— 例如几个月前的推广单现在才发布，那次合作日期的
推广成本要手动刷新那段区间才会进汇总表。这和改动 3 定的「ROI 走快照、历史不自动变」是同一个
取向，不是 bug。

### 不在本次范围

`data_source`（api 自动 / excel 手动）与「仅退款率」留在 5b-2：
- `qianniu_daily` / `ad_daily` 既没有 `import_batch_id` 也没有来源列，**历史数据无法
  回填**。光加列只会得到一列全 NULL，必须先给 RPA 与 Excel 两条写入通道各自打标。
- 「仅退款笔数」是否存在于千牛导出里尚未确认，加一个永远为 NULL 的列是负资产。

## 批次 5b-1c（PR #25）：报表读取切到汇总表（方案 2）

业务方在三个方案里选了 **2**：按 PRD 每小时刷新 + 手动刷新按钮 + 页面显示「数据更新于」，
**外加导入完成后自动刷新那批数据涉及的日期**（解决最常见的「刚导入怎么没变」）。
代价业务方已知：PR 发布一单后，工作进度不会马上 +1，要等下一次刷新。

### 什么时候读汇总表

**请求区间内每一天都有覆盖记录**才读汇总表，否则整段走实时聚合（053 的覆盖表）。不做
「刷过的日子读汇总 + 没刷过的读实时」再拼起来：投产报表按商品聚合、带 HAVING，两段各自聚合
再合并等于把 HAVING 挪到合并之后重算 —— 又写一遍聚合逻辑。整段二选一，两条路径各自完整、
各自可测。

| 报表 | 读汇总表的条件 | 说明 |
|---|---|---|
| 投产主表 | 本期区间全覆盖 | 本期、上期（环比）**各自**判断：近 30 天通常覆盖了，它的上一期往往没有 |
| 投产趋势 | 区间全覆盖 | 4 种粒度都从 `stat_date` 分桶，与实时同一份分桶模板 |
| 工作进度 | 整月全覆盖 | **当月永远实时**：月底那些还没到的日子刷不到。PR 盯着看的恰好是当月，对他们是好事 |
| 店铺数据 | 区间全覆盖 | 手填的 3 个广告消耗两条路径都是读取时 LEFT JOIN `store_daily`，填完立即生效 |
| BI 看板 | **不切** | 店铺总览是全店口径（含未归属到商品的日报），汇总表装不下；约稿金额按发布状态也没地方放。BI 显式 `use_summary=False`，整页同源，留给下一个 PR |
| 导出 | 跟页面一致 | 导出服务复用同一批 service，导出的数字与页面看到的同源 |

extra（千牛/万相台导出的其余几十列）汇总表不存，两条路径都实时。

总开关 `REPORT_SUMMARY_READS_ENABLED`（默认 True）：万一发现汇总读取与实时对不上，
改环境变量即可全部回退实时，不用回滚代码。`/metrics` 上的 `report_summary_reads_total{report,source}`
能看出切换后汇总表实际被用了多少。

### 两条路径必须逐字相等

`tests/integration/test_summary_read_equivalence.py` 24 条：投产（刷单开关 × 季节/类目筛选）、
上期也被覆盖时、趋势（4 粒度 × 刷单开关）、工作进度（14 个计数全部出现非零值）、当月必走实时、
店铺数据（含手填字段）、新鲜度判断（完整 / 缺一天 / 越界 / 总开关 / 跨租户）。

三个做法缺一不可：
- **比 JSON 而不是比 Decimal**：`model_dump(mode="json")` 逐字比。`Decimal("0") == Decimal("0.00")`
  为真，可页面上一个是「¥0」一个是「¥0.00」—— 切换数据源时用户会看到数字的样子变了
- **拦截 `record_source` 确认真的走了汇总路径**：不然两边都悄悄回退实时，比的是同一条路径，永远相等
- **场景有效性断言**：每个指标都要在场景里出现非零值，不然可能是一堆 0 在和 0 比

故障注入 4 次全部被抓：汇总读取忘了减刷单（4 条红）、覆盖判断差一天也算（2）、工作进度丢了
超时数（1）、店铺手填字段 JOIN 失效（1）。

### migration 054：补列 + 推翻 052 的一个决定

逐列核对页面后，汇总表缺两组：
- `product_roi_summary.add_cart_count`：投产报表「总加购数」「加购成本」两列靠它
- `pr_work_progress_summary` 的档期内 / 催发 / 重要催发 / 超时 4 个计数

第二组推翻了 052「这 4 个依赖今天，不存」的决定。复核后那个理由只对一半：最近 31 天每小时
按**刷新时刻的今天**重算，存的是「截至上次刷新」的状态，与其他计数同样最多晚一小时；31 天外
随历史冻结，正是 PRD「历史数据只能手动刷新」的口径。反过来不存的话，工作进度只能「10 列读
汇总 + 4 列实时」拼起来 —— PR 刚发布一单，超时数立刻 -1、发布数不动，完成率与超时率对不上。
既然业务方接受「发布后不马上更新」，那就整行一起晚。

另把两列改成不限精度的 numeric：`pr_work_progress_summary.like_count`（原 bigint）与
`product_roi_summary.refund_amount`（原 numeric(16,2)）。抖音/快手点赞按 ×0.1 折算，单日能是
1.5；逐日存整数会「先舍入再求和」，与实时的「先求和再取整」对不上 —— **等值测试真的抓到了**：
两天各 1.5，实时 3，汇总 2+2=4。

054 **清空覆盖记录**：新列加上时是 0，覆盖记录还在的话读取侧会去读一堆 0。清空后读取回退实时，
直到下一次每小时刷新把最近 31 天重写一遍。**以后任何给汇总表加列或改口径的 migration 都要做
同样的事** —— 覆盖记录是读取侧「能不能信任汇总表」的唯一依据。

### 导入完成后自动刷新

adapter 用类属性 `summary_date_field` 声明「哪一列是进报表的业务日期」：千牛/万相台 `date`、
推广单 `cooperation_date`、拍单/刷单 `order_date`。博主、款式 SKU、结算这几个来源不写汇总表依赖
的数据，不声明、不触发。runner 只记**提交成功**的行的日期，批次结束后投递一个
`refresh_report_summaries_for_dates`。

**只刷两类日子**（`summary_tasks.target_runs`）：
- 已经被覆盖的 —— 读取侧在读它的汇总行，不刷就是旧数字
- 在每小时窗口里的 —— 反正一小时内也会刷，现在刷让导入立刻可见

**没被覆盖的历史日子不刷**。它们现在走实时，数字永远是新的；刷一次反而给它们记上覆盖，从此
读汇总表、随历史冻结 —— 导入一份三个月前的 Excel，结果把那三个月从「实时」变成了「以后不手动
刷新就不会变」，这是倒退。未来的日期同理不刷。

撞上别的刷新时**重试**（60 秒一次、最多 10 次），不像每小时那次直接跳过 —— 窗口外的日子没有
「下一个小时」，丢了就一直是旧数字。投递本身失败只记日志 + Sentry，不影响导入结果。

手动刷新端点同样**截到今天**：未来的日子刷了会记上覆盖，之后才录入的未来合作日期推广单在
汇总表里就一直是 0。

### 前端

`ReportFreshness` 组件放进投产、店铺数据、工作进度三个页面的标题栏（BI 不放，它还是全实时）：
- 读汇总表：「数据更新于 HH:mm」（跨天显示日期），悬停看完整时间与刷新规则；有
  `report.summary:refresh` 权限的人多一个「刷新」按钮
- 实时：只显示「实时数据」，**不给刷新按钮** —— 实时的数字本来就是最新的，这时刷新反而会把这段
  区间切到汇总表、以后要等刷新才更新
- 撞锁（409 `REPORT_SUMMARY_REFRESH_BUSY`）提示「正在刷新中，请稍后再试」；成功后作废所有读
  汇总表的报表查询，页面立即重新取数

新鲜度走独立端点 `GET /api/reports/summaries/freshness`，而不是塞进各报表的响应：工作进度、
店铺数据两个接口返回的是裸列表，加字段就要改成信封结构，前后端分开部署的那几分钟旧前端会白屏。
`can_refresh` 由这个端点按真实权限算 —— `/me` 只返回角色，前端算不了 scope。这个端点只要求登录：
返回的是刷新时间与数据来源，不含业务数字。

用 Playwright 拦截全部接口在本地真渲染验证过：汇总 / 实时 / 撞锁 / 成功 / 无权限，以及 375 /
768 / 1440 三种宽度。第一版放在 antd Card 的 `extra` 插槽里，375px 时把标题挤成「店铺数…」，
改成标题行 flex-wrap，窄屏时新鲜度与按钮依次换行。

## 批次 5b-1d（PR #26）：报表里的退款与加购一直是 0（migration 055）

## 批次 5b-1e（PR #27）：催发阈值读配置 + 历史汇总的催发漂移 + 单篇点赞成本

## 踩过的坑（避免重复）

写 migration 与模型时反复撞到的几处，记下来省得再花时间：

- **`jsonb_build_object(:key, col)` 会抛 `IndeterminateDatatypeError`**。该函数入参声明是 `any`，PostgreSQL 推不出绑定参数的类型。必须写 `jsonb_build_object(CAST(:key AS text), col)`。046/047 的 downgrade 都栽在这里，是跑了一次真实 `alembic downgrade` 才发现的 —— 光看代码看不出来。
- **约束名会被命名约定套前缀**。`op.create_check_constraint("ck_promotion_xxx", ...)` 落库后实际叫 `ck_promotion_ck_promotion_xxx`。`op.drop_constraint` 用原名能对上（alembic 会套同样的约定），但按原名查 `pg_constraint` 查不到，验证脚本要注意。
- **数据库生成列在 async session 下会抛 `MissingGreenlet`**。SQLAlchemy 默认把 `Computed` 列当「稍后再取」，首次访问补发一条隐式 SELECT。要给模型加 `__mapper_args__ = {"eager_defaults": True}` 让 INSERT 带 RETURNING。
- **`INSERT ... SELECT ... WHERE NOT EXISTS` 同参数在两处会被推断成不同类型** → `AmbiguousParameterError`。改用 `ON CONFLICT DO NOTHING`。
- **`UPDATE ... FROM LATERAL` 引用不到 UPDATE 的目标表** → 用相关子查询。
- **类里有名为 `list` 的方法时，返回注解必须写 `builtins.list`**，否则会被解析成那个方法，类型检查静默失效。
- **模块级 `pytestmark = [..., pytest.mark.asyncio]` 会误伤同步测试** → 纯规则测试放 `tests/unit/`。
- **同一个绑定参数在一条语句里出现两次时，`::` 紧跟参数的那一处不会被替换**，留下字面量 `:today` 直接语法错误。`text()` 里一律写 `CAST(:x AS date)`。这和 046/047 的 `jsonb_build_object` 是同一个坑的两种表现，不限于那个函数。
- **`text("SELECT * FROM t").columns(*Model.__table__.columns)` 配 `scalar_one_or_none()` 返回的是第一列（id）而不是实体**，静默拿到一个 UUID，直到访问属性才炸。要取 ORM 实体就用 `select(Model)`。
- **`ruff format --check` 在 CI 里是独立一步**（`ruff check` 过了不代表 format 过），提交前要跑 `ruff format`。
- **`list_with_cte` 的 ORM 重组曾用手写列名白名单，漏列的后果是列表接口静默返回 null。** 已改成从 `Promotion.__table__.columns` 反推。往 promotion 加列时不用再动这里，但要记住：任何「手写一份列名清单」的地方都会烂。
- **测试工厂（`promotion_factory` 等）的字段清单是手写的，不认识的 kwarg 被静默忽略。** 想让某列在 DB 里有值，要么确认工厂支持那个 kwarg，要么建完直接 `UPDATE`。否则测试会在「两边都是 NULL」的情况下假通过。
- **`session.expire_all()` 之后再访问任何已加载实例的属性（哪怕是 `obj.id`）都会触发隐式加载**，在 async session 里就是 `MissingGreenlet`。要么先把需要的值取出来，要么干脆别用 ORM 实例做基准 —— 直接 `SELECT *` 拿原始行比更干净。
- **加硬约束时校验顺序要排：状态机先判，附加门槛后判。** 品牌词截图的检查一开始写在状态机之前，于是「已发布的单再点发布」报的是「缺截图」，会让人去补一张根本不需要的图。跑全量测试时才暴露。
- **`create_upload_record` 在 R2 未配置时直接抛 `AttachmentError`，没有本地回退**（`upload_bytes` 有）。测附件上传要给 `attachment_service._client` 装一个假 client，这样 Attachment 行、状态机、FK 全走真实路径，只有网络调用是假的。
- **改了已跑过的 migration 之后，本地库不会自动重跑** —— alembic 看到 revision 已是 head 就跳过。052 加权限 seed 之后查库发现权限表是空的，必须 `alembic downgrade <上一版> && alembic upgrade head` 才生效。验证 migration 的新增内容前先往返一次。
- **普通唯一索引对 NULL 不生效**。`pr_work_progress_summary` 的 `pr_id` 可为 NULL（未分配 PR 的单据也要统计），普通 `UNIQUE(tenant_id, pr_id, stat_date)` 会让「未分配」那行每次刷新都新增一条。PG 15+ 要写 `NULLS NOT DISTINCT`，而 SQLAlchemy 的 `Index(unique=True)` 表达不了，得用 `op.execute` 写原生 DDL —— 同时 ORM 侧**不要**再声明一遍这个索引，否则 `create_all` 会建出一个语义不同的。
- **权限的通配是按 action 精确匹配的**（`has()` 里 `f"{prefix}.*:{action}"`）。所以新权限的 action 取什么名字直接决定它会不会被已有通配捞走：`report.summary:read` 会自动落给持 `report.*:read` 的 operations / pr_manager，`report.summary:refresh` 不会。给敏感动作起名时先查一遍 `SELECT scope FROM permission WHERE scope LIKE '%*%'` 和谁持有它。
- **测试绿了不等于测试有效。** 等值类测试（预聚合 vs 实时、两条路径互为参照）特别容易在「两边都是 0」或「两边跑同一段错代码」的情况下静默通过。写完之后往被测代码里注入一个真实形态的故障（改错分组列、删掉 DELETE 的日期条件），确认测试会红再恢复。5b-1 的三次注入都抓到了，这才说明那 33 条有意义。另外每条等值测试都该带一个「场景有效性」断言，强制各项指标出现非零值。
- **新 model 的 FK 目标表要显式 import，否则只在 Celery 路径炸。** 5b-1 上线后生产第一次跑刷新任务就抛 `NoReferencedTableError: ... could not find table 'goods_main'`。HTTP 路径没事 —— app 启动时 router 链式 import 了全部 models；Celery 的链是 `celery_app → summary_tasks → summary_refresh_service → summary_models`，到不了 product / auth。**而本仓库的测试套件也发现不了**：`tests/conftest.py` 顶部把所有 models 都 import 了，metadata 永远完整。要在 model 模块里显式 `import` FK 指向的那些 models 模块。
- **「先删后插」在 READ COMMITTED 下不能并发。** 后一个事务的 DELETE 看不到前一个刚插入、尚未提交的行，于是它的 INSERT 卡在唯一索引上，等前一个提交后报 `UniqueViolation`。同一事务内删插只解决「读取方看不到中间态」，不解决「两个写入方互相踩」。要么拿锁（`pg_try_advisory_xact_lock`，事务级随 commit 释放），要么改 upsert。测并发必须用**两条独立连接**：`session` fixture 是单连接 + savepoint，同一事务里 advisory lock 可重入，在上面测不出任何并发问题。
- **「先跑一遍全量」的测试会掩盖「从没被刷过」的边界。** 周/月汇总缺月初那天的 bug，已有测试先做了全量刷新，月初的日汇总已经在表里，所以一直是绿的。测增量逻辑时要有一条**不做任何前置准备**的用例，直接复现生产第一次运行的形态。
- **测试与恢复操作不能放在同一批并行调用里。** 故障注入后「跑测试」和「恢复代码」一起发出去，测试可能在恢复之后才读到文件 —— 得到的绿色结果不知道是哪个版本的。注入验证必须严格串行：注入 → 跑 → 看到红 → 恢复 → 确认没有注入残留 → 再跑。
- **两条数据源路径等值，要比 JSON 而不是比 Decimal。** `Decimal("0") == Decimal("0.00")` 为真，但序列化后一个是 `"0"` 一个是 `"0.00"`。实时 SQL 在没有行时给字面量 `0`，汇总表读出来是 `0.00` —— 页面上就是「¥0」和「¥0.00」。比较用 `model_dump(mode="json")`，service 层把金额统一 quantize 到两位。
- **可加的指标，逐日存之前不能舍入。** 抖音/快手点赞 ×0.1 折算，单日能是 1.5；存成整数会「先舍入再求和」（2+2=4），实时是「先求和再取整」（3）。要预聚合的列一律存精确值，取整留到读取侧求和之后。
- **ORDER BY 有并列时，两条路径的行序不保证一致。** 实时 SQL 原来只按 `pay_amount DESC` 排，支付额相同的商品顺序随执行计划变；汇总表路径同样的 ORDER BY 换一个计划就是另一个顺序。要逐行比对两条路径，排序必须有唯一的兜底键（货号、PR 姓名 + id）。
- **测试工厂的随机字段位数太少会随机撞唯一索引。** `promotion_factory` 默认 `internal_code` 只有 3 位随机十六进制（4096 种），一个场景建十几张单、跑几十个用例，撞 `uq_promotion_internal_code` 的概率高到会随机失败。场景里批量建单时显式给足位数。
- **迁移往返与测试不能并行跑在同一个库上。** 测试连接持有表的 RowExclusiveLock，downgrade 的 `DROP TABLE` 要 AccessExclusiveLock，两边互等 → 死锁。第一次 054 往返就是这么失败的，单独重跑 rc=0。验证迁移时串行执行。
- **`configure_mappers()` 检查不出 FK 目标表缺失。** FK 的目标表是懒解析的，import 和 `configure_mappers()` 都照样成功，真正炸的地方是 flush 给相关表排序时（`mapper._sort_tables` → `fk.column`）。上面那个 bug 的第一版测试就是用 `configure_mappers()` 写的，注释掉 import 之后依然绿 —— 测了个没用的东西。要查就直接断言 `fk.target_fullname` 的目标表在 `Base.metadata.tables` 里，再编译一次 `insert()` 复现真实触发点。这类「只在某条 import 链下复现」的问题，测试必须起**干净的子进程**，不能靠 conftest 的环境。
- **测试数据按代码的假设造，等于没测。** 报表按英文键读 `qianniu_daily.extra`，测试也往 `extra` 里塞英文键 —— 两边犯同一个错，绿了五个批次，生产上退款与加购一直是 0（批次 5b-1d）。凡是读导入数据的代码，至少要有一条测试从**真实导出的样子**（原始表头、千分位、"-" 占位）开始走 adapter，而不是手写落库后的行。查生产数据时也先看真实的键集合（`jsonb_object_keys`），别默认它长成代码以为的样子。
- **JSONB 里按键取数等于没有类型检查。** 键名拼错、导入换了表头、上游从没写过这个键，查询都照样成功、只是返回 NULL / 0。报表要用的数一律落 typed 列，在导入时解析和校验；JSONB 只做原样留档。
- **依赖「今天」的派生值不能当成历史数据冻结。** 054 把催发分类落进汇总表时，把它和销售额归成「历史只能手动刷新」的同一类陈旧 —— 但销售额要有人改数据才会变，催发分类日历一走就变。往汇总表里存任何依赖当前日期的值之前，先想清楚它在窗口外会不会自己过时，以及谁来刷新它（批次 5b-1e）。
- **配置表落地之后要回头清掉所有写死的副本。** 催发阈值收进 `urge_config` 时只改了企微扫描一处，列表、详情、报表各留一份 10 / 3，后台改阈值静默不生效。收编配置的那个 PR 就该 grep 一遍常量名和字面量，并让读取方法的阈值参数**没有默认值**，漏传直接报错。
- **浏览器直传对象存储要桶上配 CORS，测试永远测不到这一点。** 付款截图走预签名 URL 直传 R2，测试里的 S3 是假的、也不经过浏览器，全绿；生产桶没配 CORS，预检 403，用户只看到一句 `Failed to fetch`。本仓库的上传一律走后端代传（PR #28 之后没有直传了）。真要直传，上线前用桶的真实预签名 URL 发一次带 `Origin` 的 OPTIONS 预检。
- **服务层 `session.rollback()` 之后，测试里再读 ORM 实例的属性就是 `MissingGreenlet`** —— 回滚让实例全部过期，读属性触发隐式加载。要比较的 id 在调用前先取出来。另外测试 session 是 savepoint 模式，要测服务的回滚路径，前置数据得先 `await session.commit()`，否则跟着一起被回滚掉。
- **「可以清空」的可选字段不能用 `if payload.x is not None` 判断有没有传。** 那样传 `null` 等于没传，字段永远清不掉。要按 `payload.model_fields_set` 判断（商品简称，PR #29）。
- **删 worktree 前先拆掉里面的目录联接（junction）。** Windows 上的 `git worktree remove` 会顺着联接往下删，把联接目标的内容也删掉。
