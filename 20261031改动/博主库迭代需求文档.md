## 0. 修订结论与范围

本轮目标是减少截图与表格录入操作，明确 PR 对接关系，让画像和作品数据可以查看，并改善谈款与留言跟进。沿用现有租户、权限、导入、流程线、通知和审批能力，按小批次交付。

2026-11-05 审阅后的主要调整：

- 推广列表的“点赞量”仍有正式列。本轮将点赞量、寄回单号默认隐藏，保留详情、指标和审核用途。
- 重新导入博主资料时保留原博主 ID 和业务关联；不清空博主库，也不删除历史推广、谈款、财务记录。
- 认领同时约束联系方式读取、修改和新合作选人；继续尊重个人权限中的显式禁止。现有在办单按原负责人继续处理。
- “沉默 5 天”先做待跟进提醒；终结动作须遵守各业务阶段的取消、召回或结算规则，不能把所有未完成单直接移走。
- 画像允许局部数据，作品补齐稳定标识和采集时间。附件模板中的公式、字段混用和爆款口径先修订，再作为导入规范。
- 多款批量操作保留主管审核、老板终审和寄送信息确认，复用单笔流程，不另建第二套审批状态机。
- 四阶段依次为：录入与列表减负 → 认领与提醒 → 卡片与待选款草稿 → 多账号报价与批量审批。真正影响业务结果的未知项保留待定，见 §10.2。

本文中的“管理员”如无特别说明，均指**租户管理员**。平台持有人使用独立平台后台排查问题，不成为客户业务经办人；指定租户的 support 会话保持只读。

## 2. 第一阶段：录入与列表减负

### 2.1 截图直接粘贴、拖拽上传（R6）

现有截图入口以选择文件为主。先盘点并接入催发、7 天数据、标记发布、驳回重提、结款截图、召回寄回、催发完成等弹窗，以及留言框、运费付款和寄回运费凭证等实际上传入口，不把原文列举的 7 处当成全量。

共用组件复用原上传接口和该入口的文件类型、大小、张数限制：

1. 支持 `Ctrl+V` 图片、拖拽和原“选择截图”按钮。
2. 监听只作用于当前可操作的弹窗或上传区，避免多个已挂载弹窗同时接收同一次粘贴。
3. 纯文本粘贴保持原行为；不因开启图片粘贴而吞掉留言文本。
4. 单图入口一次收到多张图时取第一张并提示，不擅自改变接口容量。已有多图入口按原能力处理。
5. 上传失败可重试，沿用现有附件权限；只读界面和平台 support 不显示可写上传操作。

先完成共用组件和高频入口，再补其余入口；看板逐项列出接入情况，不能仅凭组件完成就将所有入口记为完成。

### 2.2 可下载的空模板（R4 / R7）

保留“列说明”，增加“下载空模板”，先支持人工博主导入和人工站外推广导入，后续画像和作品导入沿用同一能力。

- **首个实际填报工作表仅有表头，不放示例业务行。** 示例、说明、必填规则和模板版本放独立工作表，避免原样上传时误导入示例。
- 表头与适配器解析口径同源，但只选规范字段名；别名仍用于识别旧文件，不能把每个别名都生成一列。
- 只对对应导入源实际支持的枚举生成下拉，不提前给普通博主模板塞入尚未实现的画像字段。
- 冻结表头，标识必填列和数值/日期格式。可选空白不自动解释为“清空原值”。
- 保留现有列映射与别名识别，不强制固定列顺序；模板版本用于说明数据契约，而不是排斥可映射的旧表。
- 模板下载沿用对应导入源的访问权限。R7 使用 `manual_promotion` 口径，不新增平行导入链路。

### 2.3 博主库列表精简（R1a）

从默认列表与日常编辑界面移除已不使用的分类、网页 ID、博主对接人（主/备）、是否已合流、旧阅读点赞量等展示；同类遗留的“是否添加成功”展示一并核对。列表备注列按原精简诉求隐藏，必要历史备注仍可在详情查看。

- 内容分类已迁往推广单，不能因精简博主页面而删除推广单分类。
- 网页 ID 等仍被搜索、导入或历史数据引用的字段保留存储与兼容读取，不能把“界面隐藏”写成“业务字段已彻底删除”。
- 保留博主类型、标签。标签先做列表多选筛选，不扩展到人群包和新看板。
- 本轮不删数据库列、不做全库清空；历史数据替换按 §3.4 更新原记录。

### 2.4 推广列表默认列（R12）

**现状修正**：`PromotionListPage.tsx` 仍有正式的 `like_count`“点赞量”列。`listConstants.ts` 的旧注释说的是原扩展字段被正式字段承接，不代表列表中已没有点赞量。

本轮将**点赞量、寄回单号**加入无自定义设置用户的默认隐藏项，并让“恢复默认”使用同一套新默认。已经保存列偏好的用户保留其选择。

两项仍能从列设置打开，详情、指标录入、报表和寄拍审核照常使用。寄回单号相关审核门槛不变。现有流程详情抽屉继续承担详细信息与时间线展示。

### 2.5 博主主页直达（R13）

已有 `homepage_url` 字段、录入校验、导入和列表链接，不重复建设。本轮补齐：

1. 在主页输入框粘贴分享文案时提取第一个合法 `http/https` URL，保留有效查询参数，只清理明确属于文案的尾随标点。提取成功后提示“已识别链接”。
2. 无链接时保留原文，让既有校验提示“请填写主页网址，不是账号或昵称”；不凭账号拼接主页地址。
3. 在实际复用 `BloggerSelect` 的谈款和推广创建等入口补“打开主页”，点击链接不触发选中。催发是否存在独立选择入口按代码实况处理，不假定必有第三处。
4. 卡片头部链接随第三阶段卡片交付。

引导用户从“主页 → 分享 → 复制链接”取得地址。短链可能落到作品或搜索页；本期只负责格式识别和打开用户提供的地址，不自动解析短链，也不保证外部页面永远有效。

### 2.6 旧第三方数据口径退出（R14）

业务已确定后续改用自采数据。退出分为新导入、展示和依赖处理三部分：

| 部分 | 本期处理 |
|---|---|
| 新数据入口 | 停止 `huitun`、`huitun_douyin` 新上传入口；人工博主改走统一模板 |
| 列表 | 隐藏旧爬虫/平台快照两组列；它们是不同平台视图的替换列组，不能以 35+23 断言同时展示 58 列 |
| 历史记录 | 保留源文件、导入批次、字段含义、历史冲突和处理入口；旧来源标为“历史来源” |
| 原数据 | 暂保留 `crawler_metrics`、`platform_metrics` 与旧画像数据，按需从历史详情查阅，不直接 drop 或全量清空 |
| 派生功能 | 逐项处理旧画像 `note_stats` 参与的读赞比/疑似水粉标签、定时重算、近期增长筛选等依赖 |

停止新导入不能简单删除适配器注册，使历史冲突字段或失败明细脱敏失效。可保留历史读取元数据，仅禁用新上传。

对依赖旧数据的指标和筛选，明确显示“历史数据”或“暂无可用来源”，或暂时隐藏相应筛选；不得因缺少数据就把“疑似异常”自动改成“正常”。新自采数据是否补齐小红书区间指标见 T5，不以作品明细已上线冒充所有旧指标已替代。

## 3. 第二阶段之一：认领与权限（R8 / R9 / R10）

### 3.1 业务模型

博主是**租户内共享资源池**，同一博主允许多个 PR 认领。认领是一份对接关系，不是独占权，不直接产生业绩。约篇业绩仍归业务单据的 PR，不能按认领人数或先后分摊。

- 博主唯一性继续按 `(tenant_id, platform, xiaohongshu_id)` 判断。
- 新增认领关系，包含租户、博主、PR、认领方式、操作人和时间，同一租户同一博主同一 PR 不重复创建。
- 不为认领额外长期复制一份微信明文；审计记录方式、人员和结果即可。
- 主管/租户管理员可按现有权限指定、追加、撤销和转交，变更留痕。
- 工作机名称和数量关系按 T8 确认后补充；不为未确认的多机需求预建复杂管理体系。

### 3.2 认领入口与导入衔接

| 情况 | 行为 |
|---|---|
| PR 新建全新博主 | 资料写入成功后建立本人的认领关系；仍需有相应新建权限 |
| 主管/租户管理员批量导入 | 可指定同租户有效 PR，或留待分配；不能默认把全部博主归管理员本人 |
| 已有博主，PR 输入微信号 | 输入与数据库中原有的非空微信号一致即可认领；空值不能与空值匹配成功 |
| 微信不一致或尚未登记 | 不认领，不泄露原微信值；提示联系主管核实或分配 |
| 已认领用户重复操作 | 返回已认领，不再添加关系 |
| 主管指定 | 不依赖 PR 知道微信号，但仍校验租户、目标用户和操作权限 |

微信匹配沿用系统保存口径并做一致的首尾空白处理；不任意改写账号字符。认领前比对**本次修改之前**已登记的值，禁止“先把微信改成自己输入的，再认领”。联系方式纠错由有权限的主管/管理员处理。

导入与认领分开报告：资料可能是新增、补空、重复跳过或待裁决；认领可能成功、已有或未通过。认领失败不等于可跳过导入本身的字段与权限校验。

现有同租户、同来源、同文件哈希会在逐行处理前拦截重复上传。保留该判重，不承诺第二位 PR 重传完全相同文件就会自动认领。提供直接认领/批量认领入口处理这类需求，不靠修改文件或关闭判重绕过。

### 3.3 有效读取与修改权限

认领不能替代现有角色和用户个人权限：

- 先校验租户与功能权限；个人显式禁止优先于角色授予和认领关系。
- 对有相应字段权限的人，主管/租户管理员或已认领 PR 可读取联系方式；其他人看到遮罩。未经授权不能从详情、列表、搜索、导出、导入预览/失败明细或冲突裁决旁路读到原值。
- 未认领 PR 不能修改已有博主的微信、电话，再利用新值完成认领；常规修改和导入补空/覆盖都必须检查同一规则。
- 已认领也不能绕过个人字段写入禁止。撤销认领后重新计算可见性和新合作选择范围。
- 在博主模块集中计算有效字段权限，批量读取认领关系；不通过共用权限函数“缺少行上下文就保持旧放行”留下漏口。

新增关系表和接口沿用 `tenant_id`、RLS 与同租户外键/关联校验。不同租户即使账号字符串相同，也不能互相认领、关联或读取。平台 support 可在已授权范围查看排障信息，但不能认领、修改、导入或替客户标记消息已读。

### 3.4 历史数据与在办单

“历史资料不再使用、重新采集”解释为**可以更新或替换资料内容**，不解释为删除博主实体和关联业务。

- 按租户＋平台＋账号匹配原博主，更新原记录并保留 ID；有冲突继续走现有裁决。
- 画像等专题数据是否替换由该次导入范围明确选择；空白表格不能无提示清空其他维度。
- 主管在启用新合作认领门槛前，可批量指定存量博主归属；已有在办单不因此卡住。
- **认领限制适用于新合作**：新建、复制、导入新合作、改选博主等后端入口都校验。只过滤前端下拉不算完成。
- 已有谈款/推广/召回/结算继续按原 `pr_id` 与当前业务权限推进。撤销认领不自动撤销在办单负责人，离职或交接通过主管转交。
- 历史原负责人继续处理单据，不等于自动获得被禁止的联系方式字段。

### 3.5 PR 界面与工作机

博主列表提供“全部 / 我认领的”筛选和认领状态。认领清单可查看，主管可分配；新合作选择器只返回当前用户可选的博主，并提供前往认领的路径。

工作机拟采用租户内维护的标准名称，避免“机2/二号机”无法汇总。但需先明确它指物理设备还是工作微信账号、每条认领能否同时对应多台。若只需一台主工作机，可先用单值，不强行建设设备台账。机器筛选与统计在口径确定后验收。

## 4. 第三阶段之一：画像与作品卡片（R1b / R2 / R3）

### 4.1 数据链路与更新频率

本期沿用“影刀采集/截图 → 系统外整理或解析 → 表格导入”，系统负责校验、留痕与展示，也提供手工补录。系统内不新增视觉模型调用。

| 数据 | 约定更新频率 | 范围 |
|---|---|---|
| 粉丝画像 | 半年 | 地域、城市级别、年龄、性别；按实际采到的维度更新 |
| 作品明细 | 半个月 | 作品标识、发布时间、互动指标和采集时间 |

频率用于提示资料新旧，不意味着本系统已经接管外部自动采集。系统外解析同样有成本、出错和维护责任，不能描述为“零运营成本”；维护人见 T2。手工录入和模板导入不依赖采集工具持续在线。

### 4.2 画像结构与局部数据

每个画像维度记录采集日期、来源、数值和完整性（完整分布 / 部分数据 / 估计值），支持不同维度来自不同日期。原图或源文件、导入批次、操作人进入采集记录。

- 占比限制在 0–100%；只有标为完整的同维度分布才检查合计及明确的舍入容差。部分 Top5、截图缺项不强求合计 100%。
- 导入模板明确数字百分数口径，例如 `23.5` 或 `23.5%` 表示 23.5%；比例小数不得靠猜测隐式放大，应按模板格式/映射说明处理。
- 地域省份、城市级别、年龄、性别分别存储，不能将“山东（省份视图）”写进主力城市层级。
- 年龄段保留来源标签并校验口径。附件出现 `41–50` 与 `50+` 的边界歧义须核实，不能自行改成另一套年龄分箱或假定没有重叠。
- TGI 只接收有实际来源且标注口径的值；没有来源就留空，不根据占比自行推算。性别 TGI 可展示，其他维度不为凑图表填值。
- 本次只更新提交的维度，空白不默认清空其余维度；较旧采集记录可归档但不无提示替换较新的当前值。
- 手工补录允许仅填已有维度，提供相应条目与数字输入，不以“四个下拉”代替完整分布录入。

现有 `audience_profile` 可复用，但筛选字段、作品标识/快照和采集记录可能需要结构化字段及迁移。实施时选最小可用模型，不能预先承诺“免 migration”。

### 4.3 附件模板修订契约

`抖音达人粉丝画像_数据导入模板_v1.3.xlsx` 仅作为原始样例，不能原样作为最终验收模板。本次修订的是需求文档；实际模板文件由对应开发批次更新并验证。

| 现有问题 | 开发时的处理 |
|---|---|
| 部分年龄/城市占比不足 100%，省份只有 Top5 | 标明完整性，不再统一要求合计 100% |
| 主力城市层级混入省份值 | 拆清维度，定位错误单元格提示修正 |
| 作品缺少稳定作品 ID/链接和采集时间 | 加入标识及采集时间；相同作品同一采集批次可识别重复 |
| “收藏率/分享率/评论率”公式分母实际是点赞 | 明确为“收藏/点赞、分享/点赞、评论/点赞”；播放口径若后续需要另行定义 |
| 固定“点赞≥10万”为爆款 | 改成已确认的同博主样本点赞中位数 ×3，样本范围与不足样本展示见 §4.4 |
| 原公式可能遇到零或缺少分母 | 显示空值/不可计算，不填 0、不产生除零错误 |

表头有规范名称和版本，仍兼容现有映射机制；不强制用户重排所有列。错误应定位到行/字段，避免整份文件只显示“格式错误”。

### 4.4 作品数据与爆款口径

作品只在卡片展示。字段包括平台、作品 ID 或稳定链接、发布时间、标题、赞/评/享/藏、可选播放量、采集时间、来源，以及由系统计算的互动总量和明确分母的比值。

- 作品 ID 优先；仅有链接时使用规范化后的稳定链接。标题、Excel 行号和采集顺序不能作为永久唯一标识。
- 重新采集同一作品更新该作品的展示快照并保留采集记录，不新增一条“同名新作品”；不同采集时间可追溯。
- 平台显示的 `14.3w` 等数值可复用现有数字解析，必要时保留原文；百分比需独立明确解析契约。
- 默认按发布时间倒序，可按日期范围查看；不新增任意列排序与复杂分析工具。
- 爆款采用“点赞 ≥ 同博主样本点赞中位数 ×3”。样本按所展示的采集批次/窗口计算，展示样本数量与范围，不能把跨批重复快照当多个作品。
- 全零、缺少点赞或样本不足时不自动把所有作品标成爆款；最低样本数量和显示用语在第三阶段前确认（T11）。

### 4.5 卡片与列表展示

复用已有 `BloggerHoverCard`、合作信息和自研 SVG 图表，不从零建设分析框架。

- 头部：头像/昵称、平台账号、基础规模、认领状态、打开主页。
- 粉丝画像：地域排名表、城市级别/年龄柱图、性别分布；标明采集日期、部分数据和估计值。结论必须限定在当前样本，部分数据不能宣称代表全部粉丝。
- 作品分析：样本统计、作品表和爆款提示，统计范围明确。
- 采集记录：时间、来源、操作人、批次和可访问的原文件/截图。

列表仅增加“画像更新”等必要提示，主力城市层级/主力年龄等筛选从有明确口径的数据产生。手机品牌、手机价格段、地图热力、封面抓取墙不在本期范围。

## 9. 验收标准

### 9.1 第一阶段

1. 已接入入口支持截图粘贴/拖拽，保持类型与大小限制、文本粘贴和文件选择；两个弹窗不会串收图片。
2. 模板填报页只有表头；空表不产生示例业务数据，正常填报可导入，列说明与模板规范一致，旧映射仍可使用。
3. 博主列表按精简范围展示，保留博主类型/标签及标签筛选；历史关联不因隐藏字段而断开。
4. 无保存偏好的用户默认隐藏点赞量、寄回单号；恢复默认一致；原有用户偏好保留，手动显示和审核门槛仍有效。
5. 主页输入可提取分享文案首个合法 URL，保留合法参数；无链接、纯账号和非法协议给出清楚提示，链接点击不误选博主。
6. 旧来源不再接受新上传，旧列不默认显示；旧批次、裁决和脱敏可用，派生指标缺数据时不会被误判正常。

### 9.2 第二阶段

7. 同租户多个 PR 可通过原登记非空微信完成认领；不匹配/空值不能认领，重复点击不创建重复关系，主管可指定和撤销。
8. 同一文件重复上传保持现有判重；直接/批量认领可单独完成。资料导入结果与认领结果分别可理解，不承诺重复文件自动重跑。
9. 未认领 PR 不能先改已有微信再认领；个人字段 deny 对已认领者仍生效，读写/导出/冲突/错误信息无旁路。
10. 跨租户博主、PR、认领和工作机关联被拒。平台 support 不能认领、上传或替客户标读。
11. 新建/复制/导入/改选合作的后端都检查认领；既有在办单按原负责人继续推进，撤销认领不静默转移历史业绩。
12. 重新导入保留原博主 ID 与引用；管理员可分配或留待分配，不自动认领全部导入对象。
13. 留言按最新留言/创建时间稳定排序，未读筛选可用；读过后不因“取消置顶”再次换排序。只标记本次实际看到的留言，新到消息仍未读。
14. 待跟进只提醒并筛选，不自动终结；已寄出、召回、待结款事项仍可见，不能用撤销“终结”逆转付款或物流事实。
15. 工作机和主管未读口径按 T8/T9 确认后补对应验收，不将未确认子项记为完成。

### 9.3 第三阶段

16. 部分 Top5、不完整年龄分布可导入并标注，完整分布才检查总和容差；省份与城市层级不混用。
17. 局部更新不清空其他维度，较旧采集日期不静默覆盖较新当前值，采集记录可追溯。
18. 模板补齐作品标识/采集时间；同作品重复采集不膨胀作品数，比值明确分母且零分母为空；爆款按中位数规则及已确认样本要求计算。
19. 卡片复用现有合作信息，画像/作品/采集记录可查看；显示日期与样本范围，不用局部数据作全量结论。
20. 没选款可保存“草稿·待补款”；补齐前不能提交审核、生成推广或发货，补齐后按原单笔流程运行；商品/套装关联同步校验。

### 9.4 第四阶段

21. 同账号不能同时绑定不同人；跨租户账号不能关联。未分组博主仍按原单账号报价使用。
22. 组合报价命中可带入并手改；未命中明确提示，没有确认的组合价不静默取单价相加作为成交价。
23. 单据快照账号/平台义务、约定金额和报价来源，后续改绑定或标价不改变历史单；部分平台履约结款按已确认 T7 执行。
24. 多款可共用发布日但可逐款修改，各款各价；每张单仍经过主管、老板、寄送信息确认后才生成对应推广单。
25. 批量动作逐项显示成功/未执行/失败原因；某款失败不伪装成整批成功，重试不重复生成单据；每项动作在原流程中留痕。
26. “一款一篇、同款双平台一篇”按已确认范围执行；套装和重复轮次先按 T13 明确，不能自行把套装组件数当篇数。

| T6 | 同一个人是否有同平台多个账号？组合报价按平台还是按具体账号组合？ | 不能仅用平台掩码表示账号 A/B/A+B；四阶段报价前明确 |
| T7 | 双平台约定只完成其中一个时，是否允许结款、结多少、怎么取消另一项？ | 现有多平台记录不承担结款规则，确认前不改变结款门槛 |
| T8 | 工作机指物理设备还是工作微信？一条认领是一台主机还是可挂多台？ | 认领主体可先做，机器关系和统计待定 |
| T9 | 主管“看到所有 PR 未读”是主管自己未读的全量业务留言，还是监督每位 PR 的未读清单？ | 先按用户本人维护阅读游标；监督他人未读的展示待确认，不共享已读状态 |
| T10 | 5 天按自然日还是连续 120 小时？尚未到约定发布日期的合作是否提醒？ | 默认方案供确认：连续 120 小时，以人工跟进事件计时；确认前不启定时通知 |
| T11 | 爆款最低样本数量、样本窗口和样本不足提示如何确定？ | 保留中位数 ×3 原则，不采用附件固定 10 万阈值；全零不判爆款 |
| T12 | 年龄段 `41–50` 与 `50+` 的实际边界、百分数输入格式与完整分布舍入容差？ | 以来源截图和新模板说明核定，不猜区间或隐式换算 |
| T13 | “一款”对应款式、商品还是套装？套装组件和同款重复合作轮次怎么计篇？ | 沿用现有单笔口径直至明确，不自行按组件倍增 |

## 11. 留言、谈款与多账号的详细方案

### 11.1 多账号关联与组合报价（R15，第四阶段）

先建立同一人的账号关联，保留各平台账号原记录，不做实体合并。关联组、成员和报价均在同租户内；主管可调整并留痕。未分组博主继续使用原 `blogger.quote`，不强制全库建组。

报价规则在 T6 确认后使用一种规范化组合表示，不同时维护两套容易失配的平台键和掩码。若同平台多账号存在，应能区分账号 A、账号 B、A+B，而不仅是“抖音”。

- 命中组合价时自动带入，PR 在其权限内可改成交金额。
- 未命中时提示“尚未设置此组合报价”；单价合计可作明确标注的参考，不自动当成已经约定的组合价。
- 谈款及推广记录快照约定账号/平台、成交金额、来源与合作轮次。后续改组或改标价不回写老单。
- 现有多平台发布子表主要记录平台发布事实，不足以表达同平台多账号义务和部分履约。T7 确认后再决定最小扩展，保持财务口径清楚。

### 11.2 留言未读与待跟进（R16，第二阶段）

复用流程线 `line.comment`、现有通知、未读数和顶栏入口。为每个用户维护其对流程线实际已看到的留言位置，优先用已有事件序号 `seq`，避免只用读操作发生时间误吞并发留言。

- 新留言显示未读标记，支持未读筛选；PR 按现有业务权限看自己的相关事项，主管范围在 T9 明确。
- 默认按最后留言时间（无留言取创建时间）倒序，加稳定 ID 作为同时间顺序。新单可见，读过后位置不因“取消置顶”变动。
- 平台 support 查看时间线不写客户阅读游标，也不替任何客户用户消除通知。
- 待跟进计时采用明确的人工跟进事件，例如留言、记录催发或业务处理动作；自动标签重算、无关编辑和后台任务不重置计时。具体事件清单在实现前随接口一并列明。
- 沉默达到确认阈值后进入“待跟进”筛选，可每日汇总一次并复用已配置的通知通道；不新接未授权的外部通知。
- 已完成/已取消的不再提醒；已结款但仍有其他未完成义务的情况按实际业务完成状态判断，不能仅看单一字段。

终结必须看阶段：未发生履约的谈款可使用既有取消；已寄出进入相应召回/寄回处理；有应付款项继续结算。以后若需要独立“停止跟进”，它只影响提醒，不能隐藏未完成财务/物流义务，撤销也不能回滚这些事实。

### 11.3 待选款草稿与多款批量操作（R17，第三/四阶段）

**第三阶段：草稿·待补款。** 未选款也能保存博主合作意向，显示完整性提示。提交时必须补齐该合作形式所需款式/商品/套装、金额及相关字段；校验覆盖模型、接口、表单和后续动作，不只把 `style_id` 改为可空。已有完整草稿沿用原流程。

**第四阶段：批量建立与处理。** 多选款项后生成可关联的一组单笔谈款；每单金额独立、发布日期默认共用但可逐项改。前端支持批量提交或审批，后台仍对每笔执行原权限、状态和门槛。

流程为：

`草稿补齐 → 提交主管审核 → 主管通过 → 老板终审 → 确认寄送信息 → 生成对应推广单`

每笔保留独立时间线和结果；分组只方便多选与定位，不另建一套“整批状态”。批量先展示不符合条件的项目，再逐项执行并返回结果。已有单笔动作会提交事务，不能仅套一层循环就宣称整批原子成功。失败项保持可解释状态，可只重试失败项，不重复生成推广单。

驳回哪几款就明确显示哪几款、原因和后续动作，其余款不被隐式通过或退回。套装、同款多轮与篇量按 T13 明确后实现，保留现有成本、发货和财务链路。
